01

The decision

One database per local library

SQLite owns hierarchy, revisions, generated material, answers, and media bytes. A failed save leaves the prior committed state intact.

One library per app profile. Credentials remain in OS Keychain.

Explicit domain records

Model the product that exists: source notes, static renditions, assignments, answers, and feedback. Keep source separate from generated material.

A universal block editor or arbitrary content graph can wait for a canvas decision.

Local first, deliberately

No account service, hosted database, background network work, or synchronization protocol in this increment.

Stable IDs preserve options; they do not provide sync or conflict-free merging.

SQLite describes local application data as a core use case. The recommendation above is an architectural judgment, not a performance claim. Its historical BLOB benchmarks are not evidence for StudyHub on current Apple hardware. Application use cases · BLOB tradeoffs.

Bounded snapshots agreed; capacity policy still open

Confirmed on October 24, 2026: retain bounded source notes/ink and answer snapshots so that the basis of new assignments and reviews remains inspectable. The proposed implementation retains current content plus snapshots referenced by retained assignments, the current rendition, and each assignment’s latest feedback. Reject new generation before transmission if it cannot fit; never silently delete referenced history.

The snapshot requirement is agreed. The numerical quota, reserve for continued writing, backup retention, and cleanup policy still require approval after a synthetic capacity profile. This decision does not authorize migration or application implementation.

03

A schema shaped around learning

Use nine domain tables plus one small store-metadata table. Hierarchy and relationships are relational. Native media stays binary. The answer object remains versioned JSON because generated activities legitimately vary.

Source is authoritative

A source revision captures title, text, editable native ink, and its portable preview together. A change to any provider-visible source field creates a new revision; scrolling and UI selection do not.

Static HTML, assignment HTML, and review feedback remain distinct records with distinct renderer permissions. A database row never grants script privileges.

Revision identity is durable

Preserve existing IDs as opaque text. New entities keep the existing 128-bit random ID convention. Revisions are monotonic integers within a Lecture or assignment, allocated inside the transaction.

A hash verifies bytes; it is not an entity ID, an authorization capability, or a clock. Missing legacy timestamps remain unknown.

Keep flexibility at the right boundary. Asset IDs make future relocation possible without changing domain references. A versioned answer payload supports different activities. Neither requires an event log, a generic entity-attribute-value model, CRDTs, or a canvas schema today.

Operating rules

  • One app-owned writer queue off the UI thread. Keep reads bounded: navigation queries metadata; opening a Lecture fetches only that Lecture’s active content.
  • Enforce foreign keys on every connection and verify the setting. Use composite keys to prevent cross-Lecture source links and cross-assignment answer links. The editing service still validates payloads and permissions.
  • Use expected revisions for conditional writes. A zero-row update is a conflict, not a success. Saved generation/review request IDs make repeated completion idempotent; in-process operation tokens reject canceled or superseded callbacks.
  • Continue to support one writer app instance per profile. A second instance must not silently act on stale UI state; reject write ownership or open read-only. SQLite locking is not a complete app-level cache policy.
  • Begin with rollback-journal transactions and full synchronization as the simple candidate. Verify the actual binding and Apple durability settings on both platforms. Consider WAL only if reader blocking is measured; then test checkpointing and backup explicitly.
  • Disk-full, I/O, lock-timeout, and interrupted commits leave the previous version usable. Explicitly roll back failures, reload uncertain commit outcomes, and resolve by revision/request ID before retrying.
  • Unknown database or payload versions open in a recovery/read-only path. Never “repair” an unreadable library by creating an empty one over it.

SQLite provides atomic transactions subject to its filesystem and hardware assumptions, and permits one simultaneous writer. Durability configuration is an implementation gate, not a promise that arbitrary storage cannot fail. Atomic commit · Transactions and errors · Foreign keys · Configuration.

05

Retention, backup, and privacy are part of the schema

Retain what something still needs

Roots are the current source, current answers, each saved assignment, current static rendition, and latest feedback for each assignment. An active request temporarily pins its inputs.

Collect superseded, unreferenced source/answer revisions and then unreferenced assets. Each autosave creates a revision; it does not promise permanent edit history or undo.

Pins for active calls can live in the app’s writer coordinator because background/resumable inference is out of scope. On restart there are no live callbacks; transient pins expire before collection.

Back up a consistent library

Use SQLite’s snapshot backup API, write to a new destination, run integrity and reference checks, and publish a completed backup only after validation. Failed or partial files are never offered as restorable backups.

Restore into a separate database, verify assets and schema, then switch while the store is closed. Reauthenticate providers after restore; secrets never enter exports.

A backup on the same device helps with logical corruption, not device loss. User-chosen external backup/export is a separate destination, not synchronization. SQLite backup API.

Quota recommendation to ratify

Keep the existing active-content bounds during the storage replacement. For parity, evaluate the 50 MiB active Lecture budget in its legacy-equivalent serialized form, excluding retained historical snapshots; this avoids silently expanding product limits. Add a separately approved retained-snapshot budget after profiling. Reserve room for the maximum permitted next source save. Admission checks must run before new AI work; never make a successful generation consume the last space needed to keep taking notes.

Keep 20 assignments per Lecture, 16 MiB native ink, 16 MiB preview, 4 MiB static HTML, 1 MiB assignment/feedback HTML, and a 4 MiB answer envelope. Preserve answer depth/node/key limits. The current assignment runtime limits ink to 12 canvases at 1600 × 1600 logical pixels; the current persisted-answer validator does not fully enforce image count and dimensions. Enforce these at the new storage boundary for new writes. Migration must preserve or explicitly report incompatible legacy images, never assume they satisfy runtime limits. The asset-backed answer representation is new: measure its limit using the compatible logical envelope, not just a tiny JSON reference object.

Deletion is logical, not a secure-erasure guarantee. Backups may retain deleted notes, and freed database pages or filesystem snapshots may retain bytes. Specify backup expiry and deletion expectations before shipping automatic backups. Keep credentials in Keychain; keep learner content out of logs and test fixtures. OS file protections are the baseline, not an app-managed encrypted-vault claim.

Encryption, recovery keys, unattended backup schedules, backup counts, and synchronization remain product/security decisions. This proposal does not silently select them. No new provider requests or telemetry are needed by the persistence layer.

06

A migration that can stop safely

  1. Freeze and inventory the old storeAcquire exclusive app/profile ownership. Flush and close editors; prevent old and new writers from running together. Read library v1 and referenced sidecar v1/v2 with bounded parsers. Record source hashes, IDs, order and counts. Inventory orphan and temporary files separately.
  2. Build a fresh candidate databaseNever migrate in place. Decode native ink and previews byte-for-byte into BLOBs. Preserve titles, notes, assignment IDs, definitions, answers, feedback and old revision metadata. Convert answer PNGs to asset references with a lossless round-trip check.
  3. Preserve uncertainty explicitlyThe imported current source is a snapshot at migration time. Old generation/review revision numbers do not prove historical bytes exist. Keep those original numbers as legacy provenance; use nullable historical links and “legacy context unavailable.” Never attach an old artifact to today’s source just to satisfy a foreign key.
  4. Validate before activationCompare entities and order, exact text, decoded media hashes, semantic answer values, feedback and associations. Run database integrity and foreign-key checks. Corrupt/unsupported referenced files stop whole-library cutover; they are not skipped. Preserve orphan files without resurrecting them as Lectures.
  5. Activate exactly one storeClose and flush the candidate and validate reopening. Atomically publish a small versioned active-store manifest only after the database is durable. It identifies the database and original source inventory. A crash before publication leaves JSON authoritative; after publication the database is authoritative. Validate manifest and directory durability on both platforms.
  6. Retain an explicit rollback boundaryKeep original files unchanged with migration evidence until deletion is approved. Before any new database writes, restoring the old files is lossless. After new writes, old files are stale: require a verified compatible export or restore a chosen backup with an explicit loss warning. Never silently fall back to JSON.

Old builds are a downgrade risk

An old app does not know about the new active-store manifest and can still write its old JSON paths. Activation must explain this incompatibility and prevent supported launch paths from opening the same profile with an old writer. Where that cannot be guaranteed, detect changes to the retained legacy files, block automated re-import, and offer explicit recovery/export. No claim of automatic downgrade support.

A store migration version, database structural version, payload/codec versions, and export format version are separate values. Apply future migrations in a transaction with a verified pre-migration backup. A newer unsupported version is a read-only/recovery event, never an invitation to rewrite it with an older serializer.

Measurements that decide the design

  • Compare existing JSON and candidate SQLite using the same synthetic small, typical, and near-limit libraries. Report p50/p95 save and reopen latency, main-thread stalls, peak resident memory, bytes written, database/journal growth, and backup time/space.
  • Use explicit candidate UX targets for review: no storage work blocking a frame; normal answer commits within 100 ms p95 after debounce; near-limit source commits within 500 ms p95 after snapshot capture. These are proposed targets, not current results; ratify on representative supported devices.
  • Terminate the process around each transaction/activation phase. Every restart must show a complete prior or complete new state, with no dangling references. These tests do not simulate every physical power-loss failure.
  • Verify latest-request behavior, duplicate completions, edited answers during review, record deletion during inference, and renderer refusal of untrusted content. No network call is required for persistence tests.
Fallback if the spike fails: retain JSON for the release, record the measured issue, and revisit BLOB placement or journal mode. Do not add a second asset store or broaden the schema merely to anticipate scale that has not been observed.

Updating a Lecture title also advances its source snapshot in the same transaction, because provider-visible context changed.

Deletion: owned rows cascade within a transaction. Use deferred constraints for current-head cycles; all references must be valid at commit. Asset deletion is restricted while referenced. Garbage collection derives reachability from FKs and active-request pins rather than trusting manually maintained reference counts.

The existing JavaScript bridge can continue sending its bounded data-URL form. The app validates and converts it into this storage form; restoring the assignment reconstructs the bridge form without changing stable answer keys. Never expose database asset IDs as native file paths or allow generated scripts to resolve arbitrary IDs. The host can resolve only PNGs owned by the selected assignment/revision.

PNG dimensions and byte length must be validated before decoding large buffers. Preserve text/custom values semantically during migration, including JSON number behavior supported by the current runtime. Do not claim full canonical JSON: the existing encoder preserves map iteration order rather than sorting keys. Only use a specified canonical form if a later contract truly requires it.

Static rendition and feedback rendering remain script-disabled. Assignment HTML uses the existing isolated runtime. Store explicit format/version metadata and revalidate at use/export; storage location never makes HTML trusted.

Original editable ink and preview can be retained without retaining all exported image tiles. The current export path permits up to 32 tiles / 32 MiB. These request images stay transient in this proposal; full wire replay, prompt logging, and exact exported-image retention are out of scope. This preserves source inspection but does not promise byte-for-byte reconstruction of old provider requests after renderer changes.

During a request, source/answer snapshots remain immutable and pinned. Outside the database transaction, invoke the provider with the already confirmed inputs. Before completion, validate the operation token, expected destination version and parent existence. A deleted Lecture must not be recreated by a callback. Persist one completed result idempotently and release the temporary pins on success, failure or cancellation.

Backup, export, and recovery format

Backup: a validated SQLite snapshot plus a small manifest: library identity, format version, database hash, creation time and compatibility requirement. Publish using a temporary name and atomic completion marker/rename; verify the platform’s flush behavior. Never copy an open database file as a backup. If WAL is selected later, the backup API must capture committed WAL state; copying only the main file can miss it. SQLite WAL documentation.

Portable export proposal: an archive with manifest.json, versioned hierarchy/content JSON, and media keyed by opaque IDs. Include original PencilKit bytes and PNG previews; declare that non-Apple apps may display previews without editing native strokes. Mark HTML execution policy explicitly. Validate archive paths, expanded size, hashes, IDs and supported versions before import. Export packages have no credentials, absolute local paths, or automatic remote URLs.

Recovery: retain the failed store unchanged, open a checked backup or validated candidate in a separate location, and require explicit choice if restoring loses later work. Offer deterministic integrity diagnostics containing record IDs/error codes only; no private notes or provider credentials.

What remains intentionally undecided
  • Retained-snapshot quota, backup cadence/count/destination and user-visible deletion/retention policy.
  • App-managed encryption, key recovery, and guarantees beyond OS storage protections.
  • Cloud sync, account identity, merge algorithms, remote collaboration and tombstone lifetimes. Do not sync an open SQLite file through a shared folder.
  • General canvas/block model, spatial positions, Lecture moves, cross-Lecture links, typed editing UI, voice recording/transcription retention and portable ink editing.
  • Assistant transport/discovery/authentication. Future assistants call scoped validated commands; no raw SQL, unrestricted asset access, or arbitrary JSON patches.
  • Flutter SQLite binding, journal mode tuning, compression, deduplication, and later external media storage—selected only with measured benefit.
